# PowerGrid Monitor

Монорепозиторий для мониторинга электрической сети. Симулятор и seed содержат демонстрационные данные, не предназначенные для оперативного управления.

## Структура

- `frontend/` — React, TypeScript, Vite, ECharts, Leaflet/OpenStreetMap.
- `backend/` — REST API на NestJS.
- `database/powergrid_monitor.sql` — готовая схема MariaDB/MySQL и начальные демонстрационные записи для XAMPP/phpMyAdmin.
- `simulator/` — отправка синтетических измерений в API.
- `deployment/` — Docker Compose и конфигурация Nginx.

## Локальный Запуск На Windows

1. Установите/запустите XAMPP и включите **MySQL** в панели управления.
2. Откройте `http://localhost/phpmyadmin/`, выберите **Импорт**, загрузите `database/powergrid_monitor.sql` и нажмите **Импорт**. Скрипт создаст `powergrid_monitor` и таблицы с демонстрационными справочниками.
3. По умолчанию подключение идёт к `127.0.0.1:3306`, база называется `powergrid_monitor`. При первом запуске `start-demo.bat` создаст отдельного пользователя БД с правами только на чтение и изменение данных приложения, если XAMPP `root` работает без пароля и такого пользователя ещё нет. Случайный пароль хранится зашифрованным Windows для текущей учётной записи.
4. Установите Node.js LTS версии 20.11 или новее, затем дважды щёлкните `start-demo.bat`. При первом запуске он создаст локальный сертификат HTTPS, спросит разрешение доверять локальному центру сертификации только для текущего пользователя, установит зависимости и запустит сайт, API и симулятор. Для симулятора автоматически создаётся случайный временный ключ.
5. Откройте `https://localhost:5173/`. Оставьте окна API, simulator и Vite открытыми, пока пользуетесь сайтом.

Локальный запуск привязан к `127.0.0.1`: сайт и API доступны только на этом компьютере, правило Windows Firewall не требуется. Сертификат и ключ хранятся в `%LOCALAPPDATA%\PowerGridMonitor\certs`; локальный центр сертификации доверен только текущей учётной записью Windows. Не распространяйте его закрытый ключ и не меняйте адрес прослушивания/не публикуйте порты напрямую в интернет. Без доступной MariaDB/MySQL API не запускается: приложение не переключается на временное хранение данных. Аккаунты, клиенты, обращения, заявки, аварии, телеметрия и аудит сохраняются в базе. Для остановки закройте окна API/simulator и нажмите `Ctrl+C` в окне Vite. Dev-сервер добавляет `unsafe-inline` для React Refresh; это действует только для локального Vite, production Nginx оставляет CSP без inline-скриптов. `start-demo.bat` рассчитан на Windows; Docker-сценарий ниже остаётся отдельной альтернативой.

API не подключается под `root`. После импорта схемы `start-demo.bat` автоматически создаёт отдельную учётную запись с ограниченными правами, если в локальном XAMPP доступен `root` без пароля; её случайный пароль хранится зашифрованным Windows для текущего пользователя. Если `root` уже защищён паролем или учётная запись приложения существует, создайте пользователя в phpMyAdmin под администратором БД, заменив пароль на свой случайный:

```sql
CREATE USER 'powergrid_app'@'127.0.0.1' IDENTIFIED BY 'ЗАМЕНИТЕ_НА_ДЛИННЫЙ_УНИКАЛЬНЫЙ_ПАРОЛЬ';
GRANT SELECT, INSERT, UPDATE, DELETE ON powergrid_monitor.* TO 'powergrid_app'@'127.0.0.1';
```

Если пользователь БД уже существует или `root` защищён паролем, задайте `DB_USER` и `DB_PASSWORD` в локальном терминале перед запуском. Не добавляйте пароль в исходный код и не передавайте его другим людям.

## Запуск в Docker

Требуется Docker Compose. Для локального режима скопируйте `.env.example` в `.env`, заполните три пустых поля разными случайными секретами и только затем запускайте:

```bash
cp .env.example .env
docker compose -f deployment/docker-compose.yml up --build
```

В PowerShell используйте `Copy-Item .env.example .env`. Для генерации каждого отдельного секрета выполните команду и используйте новый результат:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Docker Compose публикует веб-интерфейс только на HTTPS-порту 443, привязанном к `SITE_BIND_IP` (по умолчанию `192.168.1.20`). HTTP-порт 80 не публикуется; REST API и Socket.IO проксируются через Nginx, MariaDB и API порты наружу не публикуются. После подготовки сертификата сайт доступен в локальной сети как `https://192.168.1.20/`; задайте фактический LAN IP через `SITE_BIND_IP` и `SITE_ORIGIN` в `.env`, а при использовании production overlay также `PUBLIC_ORIGIN`. Разрешайте входящий TCP-порт 443 только своей локальной подсети. Если порт 443 занят другой службой, сначала выясните её назначение. Файл `.env` и `deployment/tls/` содержат секреты/ключи — не добавляйте их в систему контроля версий и не передавайте. Для локальной разработки устанавливайте зависимости отдельно в `frontend/` и `backend/`, затем запускайте `npm run dev` и `npm run start:dev`. Авторизация не требует аккаунтов в облаке; установка пакетов нужна только при первоначальной подготовке проекта.

## Схема сети и дашборд руководителя

Модуль «Схема сети» использует подложку OpenStreetMap и показывает состояния подстанций, оборудования и аварий из API. Направление стрелок и выбранный путь читаются сверху вниз: ТЭС → генератор → повышающий трансформатор → магистраль 110 кВ → ПС → сеть 6–10 кВ → ТП → ввод/счётчик → щит → DEMO-здание-потребитель. Цвет линий обозначает уровень/этап (генерация — фиолетовый, 110 кВ — оранжевый, 6–10 кВ — синий, 0,4 кВ — зелёный); красный, жёлтый и серый показывают аварийное, нестабильное и неизвестное состояние. Выбор узла подсвечивает демонстрационный маршрут к потребителю.

В проекте пока нет официальных координат линий, ТП и зданий и связей клиентских лицевых счетов с узлами сети. Поэтому положение объектов и топология на карте являются **условными DEMO-данными** и не показывают фактическую инфраструктуру Кокшетау. DEMO-цепочка генерации для отображения перенесена на сушу; координаты источника `53.290000, 69.338000` и условной ПС Северная `53.301000, 69.390000` проверены по обратному поиску OpenStreetMap (рядом с адресами на улицах Айдын и Абылай хан соответственно). Это не координаты реальной ТЭС или подстанции. Реальные клиенты доступны в поиске/списке, но без координат и подтверждённой привязки к ТП не размещаются на карте и им не назначается выдуманный маршрут. Для фактического маршрута нужны официальные геоданные и связи. Для OSM-подложки необходим доступ браузера в интернет; карта включает атрибуцию OpenStreetMap.

Фильтры схемы поддерживают тип объекта, напряжение, состояние и аварийные узлы. Выбор линии, ПС, ТП или DEMO-здания показывает карточку связей и записи аварий. Кнопка отключения в карточке запускает только локальный сценарий в браузере: она не записывает состояние в базу и не управляет оборудованием. Для реальной геометрии требуется загрузить проверенные официальные координаты и связи через отдельный согласованный процесс; текущая DEMO-топология для этого не предназначена.

Дашборд руководителя использует показатели из текущих записей клиентов, подстанций, заявок, телеметрии и аварий. Учётная отметка клиента и состояние счётчика не равны подтверждённому физическому отключению. Неизвестные значения не подменяются оценочными показателями.

## REST API

- `GET /api/v1/substations` и `/substations/:id`
- `GET /api/v1/equipment`
- `GET /api/v1/customers`, `POST /customers`, `GET /customers/repair-crews`
- `POST /api/v1/users/customer-account` — создать потребительский аккаунт для существующего лицевого счёта (только администратор)
- `GET`/`POST /api/v1/service-requests` и `PATCH /service-requests/:id/status`
- `GET /api/v1/telemetry/latest` и `/telemetry/history`
- `GET /api/v1/telemetry/quality` — инженерный журнал отклонённых/подозрительных сообщений
- `POST /api/v1/telemetry` для приёма измерения
- `GET /api/v1/alarms`, `POST /api/v1/alarms`, `PATCH /alarms/:id/acknowledge`, `PATCH /alarms/:id/resolve`
- `GET /api/v1/reports/load`
- `GET /api/v1/health`, `GET /api/v1/auth/status`, `GET /api/v1/audit`

Списки поддерживают `page`, `pageSize` (1–100), фильтры `from`, `to`, `equipmentId`, `substationId`, `status`, `type` и `severity` там, где они применимы. API возвращает `{ data, meta }`. Результаты ограничиваются разрешёнными подстанциями пользователя.

## Локальная Регистрация И Вход

Авторизация полностью локальная: приложение не использует внешние провайдеры, почту, OAuth или облачный сервис. Для первого запуска откройте сайт и выберите «Регистрация». Первый аккаунт автоматически становится администратором; новые регистрации получают роль «Потребитель». В разделе «Пользователи» администратор может назначать роли «Диспетчер», «Инженер» и «Администратор», а также создавать учётную запись для существующего лицевого счёта: выберите потребителя и задайте ему отдельные логин и пароль длиной не менее 10 символов. Учётка связывается с текущей записью и не создаёт дубликат лицевого счёта. Передайте пароль потребителю безопасным способом; пароль хранится только в виде криптографического хеша.

Учётные записи, хеши паролей и ключ подписи сессий хранятся в таблицах MySQL `users` и `app_settings`; сессия действует 12 часов. Для резервной копии экспортируйте базу `powergrid_monitor` из phpMyAdmin. Демо-токен симулятора нужен только для синтетической телеметрии и не является пользовательским входом.

Статус локальной регистрации доступен в `GET /api/v1/auth/status`, регистрация — `POST /api/v1/auth/register`, вход — `POST /api/v1/auth/login`. Все остальные API требуют локальный access token.

## Защита сайта

- По умолчанию сайт и API слушают только loopback (`127.0.0.1`); CORS разрешает только локальный frontend. Не открывайте сайт по адресу сети и не пробрасывайте порты роутера.
- Backend выставляет защитные HTTP-заголовки и Content Security Policy; Nginx применяет их также к статическим страницам. В CSP разрешены только скрипты с этого же сайта.
- Вход ограничен 5 запросами в минуту, регистрация — 3 запросами в минуту; для API действует общий лимит. При Docker-запуске Nginx добавляет лимиты запросов и соединений.
- Администратор может привязать локальную учётную запись к существующему лицевому счёту; каждый потребитель должен получить собственный пароль, который показывается/передаётся администратором только при создании.
- Секрет симулятора в `start-demo.bat` генерируется случайно при запуске. Не используйте известные или демонстрационные значения `SIMULATOR_TOKEN`.
- Для Docker задавайте отдельные длинные случайные `MARIADB_ROOT_PASSWORD`, `MARIADB_APP_PASSWORD` и `SIMULATOR_TOKEN`. Секреты из `.env.example` — только заполнители.
- В XAMPP используйте отдельную учётную запись БД с минимальными правами, описанную выше; не используйте `root` без пароля.
- Локальный HTTP подходит только для использования на этом компьютере. Для доступа других устройств или публикации через интернет сначала настройте HTTPS reverse proxy и ограничьте доступ на сетевом уровне; не выставляйте порты Vite, API, MySQL или phpMyAdmin в интернет.
- `npm audit --omit=dev` по-прежнему сообщает об умеренных проблемах в текущей ветке NestJS 10 и её `file-type`; автоматическое исправление предлагает major-обновление NestJS. Перед интернет-публикацией обновите NestJS и повторно проверьте сборку и поведение API.

Socket.IO namespace `/telemetry` отправляет событие `telemetry.measurement` только клиентам с доступом к соответствующей подстанции. Клиент автоматически переподключается и после каждого reconnect повторно запрашивает latest snapshot. Запросы ограничиваются NestJS и Nginx rate limit.

Поддержка работает через REST `/api/v1/support` и Socket.IO namespace `/support`: обращения и сообщения сохраняются в MySQL. Для очереди и ответов нужны аккаунты с ролью «Диспетчер», «Инженер» или «Администратор». Откройте портал во втором окне и войдите под аккаунтом оператора; обращения появляются в очереди сразу. На другом устройстве в локальной сети откройте сайт по IP компьютера с Vite. Локальный rule-based ИИ-ассистент не является онлайн-оператором.

## Данные

- MariaDB/MySQL хранит локальные аккаунты и роли, оборудование, клиентов и показания, заявки, обращения поддержки, измерения телеметрии, аварии, источники и аудит.
- API сохраняет измерения в `telemetry`; `GET /telemetry/latest` и `/history` поддерживают пагинацию и временные/object-фильтры.
- Измерения старше 10 минут отклоняются и попадают в `telemetry_quality_events`; повторы для пары equipment/timestamp получают HTTP 409.
- Технические выбросы сохраняются с `quality_status=suspect` и quality flags, но не создают аварии автоматически. Demo guardrails: напряжение 1–500 кВ и 80–120% номинала, ток до 20 кА, абсолютная мощность до 5000 МВт, частота 45–55 Гц. Эти широкие значения нужно заменить профилями конкретного оборудования перед эксплуатацией.
- Heartbeat обновляется при каждом принятом сообщении; источник становится offline через 15 секунд без связи. Невалидное/устаревшее значение не считается аварией оборудования; состояние API и источника показывается отдельно.
- Мутации API записываются в `audit_logs`; тело запроса не сохраняется, только список имён полей.
- Для запуска API база обязательна; ошибки соединения показываются явно, временный in-memory fallback отключён.
- PostgreSQL migrations в `database/migrations/` оставлены для старых инсталляций и не используются XAMPP-приложением. Новая схема для импорта: `database/powergrid_monitor.sql`.

## Клиенты И Ремонт

В demo-интерфейсе доступны:

- Dashboard руководителя: потребление по домам, месячные начисления, долги и заявки на проверке.
- Реестр потребителей: лицевые ID `CL-*`, smart meter ID `SM-*`, текущие/прошлые показания и начисление по тарифу.
- Реестр показывает статус электропитания из `customers.supply_status`: `unknown`, `connected` или `disconnected`. До фактического подтверждения статус не предполагается автоматически. Диспетчер/администратор может записать подтверждённую отметку в БД; это не команда оборудованию. Для существующей MariaDB выполните `database/migrations/005_customer_supply_status.mysql.sql`; новые клиенты по умолчанию получают статус `unknown`.
- Для сотрудников с ролями «Диспетчер» и «Администратор» в реестре каждого потребителя есть запросы на проверку отключения при ненулевом долге и на восстановление. Они создают `service_requests` в MariaDB, проверяют долг на сервере и предотвращают дубликаты активных запросов; электроснабжение и оборудование не переключаются.
- Demo тариф — `31,20 ₸/кВт·ч`; он не является официальным тарифом. Суммы и задолженности учебные.
- Заявки на новое подключение и проверку задолженности.
- Форма «Оставить заявку» в разделе ремонтных бригад: клиент, приоритет и описание неисправности. Новая заявка появляется в очереди со статусом «Ожидает проверки».
- Реестр demo-ремонтных бригад, назначение выезда и закрытие осмотра.
- Корпоративный portal со счётом и расходом smart meter; консультация с оператором использует REST API и realtime-канал, а пользователям с ролью оператора показывает очередь обращений и отправку ответа. ИИ-ассистент остаётся rule-based демо-функцией.

Демо-клиентские записи, показания, начисления, подстанции, оборудование и ремонтные бригады загружаются из MySQL; графики и показатели телеметрии строятся по сохранённым измерениям. Создание клиентов, обращений и изменение статуса заявок записывается в БД. Координаты узлов на схеме остаются настройкой отображения в интерфейсе. Реальная оплата и отправка SMS/email не подключены. Долг создаёт только задачу на проверку: отключение за неоплату, подключение нового клиента и remote switching не исполняются автоматически. Кнопки переключения создают заявку на ручное согласование; прямого управления физическим оборудованием нет.

Демо-события обрыва линии и технического превышения являются примерами интерфейса, а не обнаружением аварии реального оборудования. Подозрительные показания маркируются как проблема качества данных и требуют проверки датчика/источника.

## Production И OT

Для защищённого доступа к Kali в локальной сети можно создать сертификат для её IP с локальным CA. На сервере (пример IP `192.168.1.20`):

```bash
sudo apt install mkcert
mkcert -install
mkdir -p deployment/tls
mkcert -cert-file deployment/tls/tls.crt -key-file deployment/tls/tls.key 192.168.1.20
chmod 600 deployment/tls/tls.key
mkcert -CAROOT
```

Скопируйте **только** `rootCA.pem` из каталога, показанного `mkcert -CAROOT`, на соседний компьютер. В Windows запустите PowerShell от имени администратора и выполните `certutil -addstore -f Root .\rootCA.pem`; затем перезапустите браузер. Не копируйте `rootCA-key.pem` или `tls.key`: ими можно подделать сертификаты. Сайт откроется как `https://192.168.1.20/` без предупреждения. Этот локальный CA подходит только для контролируемой LAN-тестовой среды, не для публичного сайта.

Запуск в Kali:

```bash
docker compose -f deployment/docker-compose.yml up --build -d
```

Для UFW разрешите TCP 443 только своей подсети:

```bash
sudo ufw allow from 192.168.1.0/25 to 192.168.1.20 port 443 proto tcp
```

Docker может обходить обычные UFW-фильтры для опубликованных портов, поэтому Compose привязывает HTTPS именно к LAN IP, не ко всем интерфейсам. Не настраивайте переадресацию портов на роутере; другие устройства той же подсети смогут открыть сайт. Apache на порту 80 не конфликтует: HTTP-порт хоста не публикуется. Nginx разрешает TLS 1.2/1.3 и включает HSTS и security headers. Локальный сценарий `start-demo.bat` использует HTTPS на `https://localhost:5173/`; его самоподписанный локальный сертификат предназначен только для разработки.

Docker разделяет edge и internal сети: наружу публикуется только Nginx, MariaDB и backend ports не публикуются, simulator не соединён с edge-сетью. Backend принимает API только через reverse proxy и внутреннюю сеть. В приложении нет команд прямого управления оборудованием. Для реальной телеметрии используйте разрешённый шлюз, отдельный от OT-сети; не подключайте backend или браузер напрямую к промышленным устройствам. Изменения и security-тесты сначала проверяйте на изолированной среде с синтетическими данными.

Контейнеры настроены на автоматический restart и health checks. Backup service делает ежедневный `mariadb-dump` и хранит последние 7 дней в `mysql-backups`; процедуру восстановления нужно регулярно проверять на отдельной среде. Полное резервирование серверов, внешнее мониторирование свободного места/нагрузки, сетевой firewall, UPS и тест восстановления инфраструктуры остаются задачей production deployment, а не гарантируются локальным Compose. Внешний firewall должен разрешать только HTTPS к Nginx и необходимые административные направления.

Главная сводка показывает состояние API отдельно от источника и freshness измерения; доступность сайта не означает доступность электросети. Compose применяет SQL-файлы только при первом создании пустого volume. Для существующей БД запускайте новые SQL migrations вручную перед обновлением backend.
